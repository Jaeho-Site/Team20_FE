# 리팩토링 목표와 실험 계획 (2026-07-28)

이 문서는 분석·로드맵의 우선순위 기준이다. 분석 세션은 이 문서를 먼저 읽고, 발견한 부채 항목이 아래 실험 중 어느 것의 사전 작업인지 연결한다.

## 최종 목표

1. **기술 부채 전면 해소** — 미사용 의존성·데드 코드·명백한 비효율 제거. 단, 제거도 수치(번들 diff, 의존성 수, 줄 수)와 함께 기록한다.
2. **대체 기술과의 정량 비교** — 부채를 그냥 고치는 게 아니라, 선택지를 실제로 구현·측정해 `docs/refactor/`에 남기는 것이 이 저장소의 산출물이다. 수치 없는 개선은 결과물로 치지 않는다.

## 실험 목록 (예상 비용 순 아님 — 우선순위는 로드맵에서 결정)

| # | 실험 | 방식 | 지표 후보 |
|---|---|---|---|
| A | zod × TanStack Form 결합 최적화 | 리팩토링 (before/after) | 스키마 중복 수, 타입 단언 수, 폼당 코드 줄 수 |
| B | TanStack Form vs React Hook Form | `/ab-compare` (auth 폼, zod 스키마 공유) | 라이브러리 기여분 gzip, 코드량, 리렌더 횟수 |
| C | next/image vs `<img>` | `/ab-compare` (**같은 nextjs 앱 안에서** 비교 — 프레임워크 교란 변수 차단) | LCP, 이미지 전송 bytes, CLS, 포맷 협상(webp/avif) |

## 이미 정해진 것

- 실험 절차는 `/ab-compare`, 리팩토링 절차는 `/refactor-safely`를 따른다.
- 부채 제거 → **재측정(baseline 갱신)** → 실험 순서로 간다. 부채가 섞인 상태에서 잰 비교 수치는 원인 귀속이 안 된다.
- 부정적 결과(차이 없음, 직관과 반대)도 그대로 기록한다. 그것이 가장 가치 있는 결과다.

## 아직 결정 안 된 것 (분석 세션이 AskUserQuestion으로 물을 것)

- **정본 워크스페이스**: 루트(Vite)를 정본으로 유지하는 방향으로 기울어 있음. nextjs/는 실험 C의 실험장으로만 유지하고 드리프트를 의도적으로 허용할지, 동기화를 유지할지 결정 필요.
- **단위 테스트 러너 도입 시점**: 실험 A·B(폼·스키마)는 단위 테스트가 있어야 회귀를 잡을 수 있다. vitest 도입을 실험보다 먼저 할지 결정 필요.
