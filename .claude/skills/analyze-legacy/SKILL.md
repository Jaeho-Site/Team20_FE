# 레거시 분석 절차

범위: $ARGUMENTS (비어 있으면 저장소 전체)

## 원칙

- **읽기만 한다.** 이 절차에서는 코드를 고치지 않는다. 발견과 수정을 섞으면 둘 다 어설퍼진다.
- 조사는 subagent에 위임한다. 메인 대화에서 수십 개 파일을 직접 읽지 않는다.
- 결과는 반드시 `docs/refactor/`에 파일로 남긴다. 대화는 압축되면 사라진다.

## 1단계 — 지형 파악 (메인 대화, 10분)

먼저 저렴한 수단으로 전체 모양만 잡는다. 파일을 통째로 읽지 않는다.

```bash
git log --oneline -30                       # 최근 무슨 작업이 있었나
git log --format='%ad' --date=short | sort -u | tail -5   # 마지막 활동 시점
find src nextjs/src -name "*.ts*" | xargs wc -l | sort -rn | head -20   # 큰 파일
npm ls --depth=0 2>&1 | head -40            # 실제 설치된 의존성 (node_modules 필요)
```

여기서 나온 관찰을 바탕으로 2단계의 조사 범위를 **구체적으로** 나눈다.

## 2단계 — 병렬 조사 (subagent 위임)

아래 조사를 **한 메시지에서 동시에** 띄운다. 각 subagent에는 범위를 명시한다.

| subagent | 위임 내용 |
|---|---|
| `legacy-auditor` | 루트 `src/` 기술 부채 감사 (레이어 위반, 데드 코드, 미사용 export, 검증 공백) |
| `legacy-auditor` | TanStack Query/Router/Form 사용 실태 — 안티패턴과 잘못 쓰인 지점 |
| `migration-differ` | `src/` vs `nextjs/src/` 중복·드리프트 현황 |
| `legacy-auditor` | `functions/itinerary_theme/` 파이썬 함수 (main.py 459줄 분해 가능성 중심) |

범위가 좁게 지정됐다면(`$ARGUMENTS`가 있다면) 해당하는 것만 띄운다.

## 3단계 — 종합

각 subagent의 요약을 받아 **중복을 제거하고 우선순위를 매긴다.** 우선순위 기준:

1. 정확성 위험 (사용자에게 실제로 영향)
2. 변경을 막고 있는 것 (검증 수단 부재, 중복 구현)
3. 목표에 직결되는 것 (TanStack/zod 활용 정리 — 이 저장소의 핵심 관심사)
4. 정리하면 좋은 것

각 항목에 **측정 가능한 지표**를 붙인다. "복잡하다"가 아니라 "459줄, 함수 12개, 최대 중첩 5단계"처럼 쓴다. 지표가 없으면 나중에 개선을 증명할 수 없다.

## 4단계 — 문서화

`docs/refactor/00-analysis.md`를 만들고 다음을 담는다.

```markdown
# 레거시 분석 (YYYY-MM-DD)

## 현황 수치 (baseline)
| 지표 | 값 |
(파일 수, 총 줄 수, 번들 크기, 중복 파일 수, 미사용 의존성 수, 테스트 커버리지 부재 범위 …)

## 발견 사항 (우선순위 순)
### 1. 제목
- 근거: path:line
- 영향:
- 측정 지표: (개선을 증명할 수치)
- 예상 작업 규모:

## 리팩토링 로드맵
(순서와 그 순서인 이유. 의존 관계 명시)

## 판단 보류
(사용자 결정이 필요한 것 — 예: vite/nextjs 중 어느 쪽을 정본으로 삼을지)
```

## 5단계 — 사용자에게 보고

문서 경로와 함께 **최상위 발견 5개, 권고 다음 행동 1개**만 대화에 요약한다. 문서 내용을 대화에 다시 붙여넣지 않는다.

사용자 결정이 필요한 항목이 있으면 `AskUserQuestion`으로 선택지를 제시한다. 특히 다음은 반드시 확인한다:

- 루트(Vite)와 `nextjs/` 중 무엇을 정본으로 유지할 것인가
- 검증 수단(단위 테스트) 도입을 리팩토링보다 먼저 할 것인가
