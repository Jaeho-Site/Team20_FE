# 안전한 리팩토링 절차

대상: $ARGUMENTS

이 저장소에는 단위 테스트 러너가 없다. 검증 수단이 약하다는 것은 **작업 단위를 더 작게 쪼개야 한다**는 뜻이지, 검증을 건너뛰어도 된다는 뜻이 아니다.

## 1. 착수 전 체크 (하나라도 실패하면 멈추고 보고)

```bash
git status --short          # 작업 트리가 clean한가
git branch --show-current   # main이면 브랜치를 먼저 만든다
ls node_modules >/dev/null  # 없으면 npm install
```

- 어느 워크스페이스를 고치는가? (루트 / nextjs) — **양쪽 중복 파일 중 한쪽만 고치면 드리프트가 생긴다.** 다른 쪽을 어떻게 할지 지금 정한다.
- 이 변경이 깨졌을 때 **무엇을 보고 알 수 있는가?** 답이 없으면 리팩토링 전에 검증 수단부터 만든다.

## 2. Baseline 확보

변경 전 상태에서 `benchmark-runner` subagent로 측정한다. 최소한:

- `npm run type-check` / `npm run lint` / `npm run build` 통과 여부
- 대상 파일의 줄 수, 관련 번들 크기

**baseline이 이미 실패 상태라면 그 사실을 먼저 기록한다.** 원래 깨져 있던 것을 내 변경 탓으로 오인하는 일을 막는다.

## 3. 변경

- 한 번에 **하나의 관심사**만 바꾼다. 중복 제거와 API 변경을 같은 커밋에 섞지 않는다.
- 동작을 바꾸는 변경(behavior change)과 구조만 바꾸는 변경(pure refactor)을 분리한다. 섞이면 회귀 원인을 못 찾는다.
- FSD 레이어를 넘나드는 이동은 `index.ts` public API 갱신을 동반한다.
- 편집 후 포맷은 hook이 자동 처리한다. 수동으로 맞추지 말 것.

## 4. 검증 (건너뛰지 않는다)

```bash
npm run type-check
npm run lint
npm run build
```

- 셋 다 통과해야 다음으로 간다. 실패하면 되돌리거나 고친다. **"나중에 고치겠다"로 넘어가지 않는다.**
- UI 동작이 바뀔 수 있는 변경이면 `npm run test:e2e`를 검토한다 (환경변수·서버 필요 — 못 돌리면 그 사실을 보고에 명시).
- 변경 후 `benchmark-runner`로 재측정해 baseline과 비교한다.

## 5. 적대적 검토

`code-reviewer` subagent를 호출한다. 방금 코드를 쓴 컨텍스트는 자기 코드에 편향돼 있으므로, 새 컨텍스트의 리뷰가 실질적인 두 번째 의견이 된다.

리뷰 결과를 **전부 반영하지는 않는다.** 정확성과 명시된 요구사항에 영향을 주는 것만 고치고, 나머지는 판단 근거와 함께 넘긴다.

## 6. 보고

```
## 무엇을 바꿨나
(한 문단)

## 검증 증거
$ npm run type-check   → (실제 출력 요약)
$ npm run lint         → (실제 출력 요약)
$ npm run build        → (실제 출력 요약)

## 수치 변화
| 지표 | before | after | 차이 |

## 검토 결과 반영 여부
(리뷰 지적 중 고친 것 / 넘긴 것과 그 이유)

## 남긴 것
(범위 밖으로 판단해 손대지 않은 것, 생긴 드리프트)
```

**증거 없는 완료 보고는 하지 않는다.** 실행하지 않은 명령을 실행한 것처럼 적지 않는다. 못 돌렸으면 "못 돌림 + 이유"라고 쓴다.

## 7. 기록

의미 있는 변화(수치가 움직인 작업)는 `docs/refactor/`에 한 섹션으로 추가한다.
